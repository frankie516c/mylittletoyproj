[1] 준비한 프롬프트
--------------------------------------------------------------------------------

"루프 엔지니어링 할거야. 너는 내가 정한 목표를 달성할때까지 정해진 워크플로우에 따라서
문제 분석, 가정, 실험과 평가를 반복하면서 계속 알아서 개선작업을 진행해. 목표는 준비한
평가데이터의 인식율(위드단위)을 90% 달성할때까지 반복하는거야. 태스크는 ocr이고 모델은
qwen 3.5 0.8b 모델을 대상으로 할거고, 일단 평가 데이터부터 준비해줘. 영수증 데이터 학습
데이터 10장 평가데이터 3장 준비해서 진행해주면 돼. 매회 루프 돌때마다 해당 루프를
워크플로우로 실행해줘."


--------------------------------------------------------------------------------
[2] ralph-loop 플러그인이란
--------------------------------------------------------------------------------

Anthropic 마켓플레이스 플러그인. 이 PC에는 아직 설치되어 있지 않다.

  설명 : Interactive self-referential AI loops for iterative development,
         implementing the Ralph Wiggum technique. Claude works on the same task
         repeatedly, seeing its previous work, until completion.
  명령 : /ralph-loop, /cancel-ralph, /help
  구현 : Stop 훅. 세션이 종료되려 하면 훅이 같은 프롬프트를 다시 밀어 넣는다.

핵심 성질은 "완료될 때까지 같은 과제를 붙든다"이다. 따라서 **완료 판정이 존재하는
과제에만** 맞는 도구다. 테스트가 빨강에서 초록으로 바뀌는 상황이 전형적인 예다.


--------------------------------------------------------------------------------
[3] 이 저장소의 RAG 파이프라인에 ralph-loop을 걸면 (실제 코드 기준 검토)
--------------------------------------------------------------------------------

결론부터: 지금 상태로는 걸면 안 된다. 문제가 코드에 구체적으로 박혀 있다.

 (1) ASPCA / AKC / HSUS 를 반복 크롤링한다
     ingest.py 는 --skip-fetch 가 없으면 매 실행마다 10개 URL 을 전부 재요청한다.
     robots.txt 확인, rate limit, 조건부 GET(etag/if-modified-since), 백오프가
     전부 없다. 한 IP 에서 시간당 수십 번 두드리게 된다.

 (2) 코퍼스가 조용히 줄어든다
     차단당하면 collect_markdown 이 실패한 소스를 건너뛰고 계속 진행하도록
     되어 있다. 155개였던 청크가 어느 순간 90개가 되고, 지표는 움직이는데
     원인은 모델과 아무 상관이 없다.

 (3) 인덱스가 비어버릴 수 있다
     recreate_collection 은 delete -> create -> upsert 순서이고 원자적이지 않다.
     중간에 죽으면 빈 컬렉션이 남는다. 반복해도 코퍼스가 누적되지 않는다.

 (4) 락 충돌
     Qdrant 임베디드 모드는 저장 디렉터리를 잠근다. 이전 반복이나 서버가
     잡고 있으면 다음 반복이 열지 못한다.

 (5) 평가 기준이 매 반복마다 바뀐다  <-- 가장 나쁜 문제
     make_evalset.py 는 seed 42 로 고정돼 있지만, 표본을 뽑는 풀 자체가 현재
     chunks.jsonl 에서 만들어진다. 코퍼스가 한 청크라도 바뀌면 seed 42 가 다른
     청크를 고른다. 질문도 매번 temperature 0.4 로 새로 생성된다. 게다가
     golden_v1.jsonl 을 덮어쓰기 때문에 이전 기준선이 사라진다.
     결과적으로 반복마다 나오는 hit rate 는 서로 다른 시험지의 점수다.
     0.10 -> 0.35 -> 0.20 그래프를 봐도 개선인지 노이즈인지 구분할 수 없다.

 (6) 끝나지 않는다
     evaluate.py 는 점수와 무관하게 exit 0 이다. "until completion" 의 완료
     판정이 없으므로 Stop 훅이 무한히 재주입한다.

 (7) 진짜 문제를 못 고친다
     측정된 병목은 top-20 점수 폭이 0.0125 라는 것이다. 임베딩이 모든 청크에
     사실상 같은 점수를 주고 있어 순위가 노이즈다. 크롤링을 더 하고 다시
     임베딩하고 질문을 새로 만드는 것은 이 숫자를 건드리지 않는다.

 (8) 루프는 시험지를 쉽게 만드는 쪽으로 수렴한다
     "hit rate 를 올려라" 로 루프를 걸면, 가장 싼 경로는 벤치마크를 완화하는
     것이다. 질문을 더 단순하게 재생성하거나, 정답 판정을 문서 단위로 바꾸거나,
     k 를 키우거나. 전부 루프가 편집할 수 있는 파일에서 한 줄이면 된다.
     hit@5 = 0.9 를 받아들고 아무것도 배우지 못하게 된다.


--------------------------------------------------------------------------------
[4] 루프를 걸 수 있는 상태로 만들려면 (순서대로)
--------------------------------------------------------------------------------

 1. 먼저 compare_models.py 를 한 번 돌린다. 루프가 아니라 단발.
    양자화가 원인이면 나머지 작업은 전부 무의미하다.

 2. 평가셋 동결.
    golden_v1.jsonl 을 읽기 전용 기준선으로 고정하고, make_evalset.py 가
    기존 파일을 덮어쓰지 못하게 막는다.

 3. 크롤링과 색인 분리.
    루프에서는 --skip-fetch 를 강제한다. 재크롤은 조건부 GET 을 붙인 뒤
    별도 주기로 돌린다.

 4. recreate_collection 을 upsert 로 바꾼다.
    hash(doc_id + chunk_index) 를 포인트 id 로 써서 멱등하게 만든다.

 5. 종료 게이트를 만든다.
    evaluate.py 가 hit@5 < 기준선이면 exit 1 을 내도록 한다.
    그래야 루프에 완료 판정이 생긴다.

 6. 그다음에야 루프가 의미를 갖는다. 그때도 같은 실행의 반복이 아니라
    스윕이어야 한다. 청크 크기 x 임베딩 모델 x 하이브리드 on/off.

4번과 5번까지 되면 사실 ralph-loop 이 아니어도 된다. Claude Code 에 내장된
/loop (주기 실행) 이나 schedule (cron) 로 충분하다. Ralph 방식은 "테스트가
빨강에서 초록이 될 때까지 같은 과제를 붙든다" 에 맞는 도구이고, 지금은 초록
판정 자체가 없는 상태다.


--------------------------------------------------------------------------------
[5] [1] 의 OCR 프롬프트에 그대로 적용했을 때 예상되는 문제
--------------------------------------------------------------------------------

위 (1)~(8) 중 상당수가 OCR 과제에도 그대로 옮겨 붙는다. 특히:

 - 목표가 "워드 단위 인식률 90%" 로 명확한 것은 좋다. (5)(6) 의 완료 판정
   문제는 해결된다. 다만 채점 스크립트가 exit code 로 성공/실패를 내야 한다.
   숫자만 출력하고 exit 0 이면 루프는 멈추지 않는다.

 - 평가 데이터 3장은 너무 적다. 한 장이 통째로 맞고 틀림에 따라 인식률이
   30% 단위로 튄다. 90% 달성 여부가 표본 노이즈에 좌우되므로, 개선을
   측정하는 도구로 쓸 수 없다. 최소 20~30장은 필요하다.

 - 평가 데이터를 루프 안에서 생성하면 안 된다. (5) 와 같은 함정이다.
   학습 10장 / 평가 3장을 먼저 만들고 동결한 뒤, 루프는 그 파일을 읽기만
   해야 한다.

 - 학습 10장으로 파인튜닝하면 거의 확실히 과적합한다. 10장으로 올린 점수가
   3장짜리 평가셋에서 90%를 찍어도 일반화 근거가 되지 않는다.

 - 정답 라벨(ground truth)을 누가 만드는지가 빠져 있다. 영수증 OCR 은
   띄어쓰기, 금액 구분자, 줄바꿈 처리 규칙에 따라 워드 단위 점수가 크게
   달라진다. 채점 정규화 규칙을 먼저 문서로 고정해야 한다.

 - Qwen 3.5 0.8B 라는 모델명은 실재 여부를 확인하지 않았다. 루프를 걸기 전에
   모델 카드와 OCR 지원 여부(vision 입력 가능한지)를 먼저 확인해야 한다.

권고: 루프를 걸기 전에 (a) 평가셋 20장 이상 확보 및 동결, (b) 채점 정규화
규칙 문서화, (c) 채점 스크립트가 exit code 를 내도록 구현, (d) 베이스라인
1회 측정. 이 넷이 끝난 뒤에 루프를 건다.
